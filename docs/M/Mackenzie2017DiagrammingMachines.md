# Thesis job

**Contribution to the primary question:** Mackenzie shows why the operations that render information computationally knowable cannot be understood solely from code, model outputs or attractive visualisations. His diagrammatic approach allows me to examine the relations among documentary inputs, mathematical representations, software libraries, pedagogical conventions, research decisions and public interfaces that comprise the DDR instrument.

**Secondary-question relevance:** The chapter offers a method for interrogating the *contemporary instruments* through which DDR-era ideas become retrievable and comparable. It cannot itself decide what design knowledge from the DDR period merits recovery or revision; that requires historical source analysis.

**Why read this chapter now:** Chapter 1 proposed an archaeology of operations; Chapter 2 develops its method in concrete experiments with elementary machine learners, influential textbooks, citation networks, R packages, mathematical expressions and handwritten mathematical teaching. My own layered practice-led instrument similarly crosses documentary, technical and designed forms, but the analogy must be demonstrated, not assumed.

**My benchmark for use:** (1) A diagram must expose a real, inspectable operation or dependency and clarify what it changes in the research evidence; (2) the account must preserve distinctions between source material, computational relation, interface display and historically warranted inference.

# Position and context

The chapter opens by challenging the apparently effortless image of models that 'grow' programs from data. Mackenzie instead situates learning in a distributed material field of documents, code, laboratories, diagrams, online courses, mathematical techniques and software libraries (pp. 21–23). He juxtaposes a Boolean **NAND** truth table with a Python perceptron implementation (pp. 23–27), narrates his own multi-format study of machine learning (pp. 27–30), and treats *The Elements of Statistical Learning* as a networked object traversed by disciplines, citations, diagrams and R code (pp. 30–40). He then examines mathematical expression and manual transcription as diagrammatic practices (pp. 40–46), compares historical and later representations of the perceptron (pp. 46–48), and concludes that algorithms travel through heterogeneous formal, computational and institutional arrangements (pp. 49–50).

**Important scope qualification:** Mackenzie explicitly acknowledges that his archaeology does **not** examine the actual archives of laboratories, companies or institutions where machine-learning techniques developed (p. 47, note 9, continuing on p. 48). His genealogy is traced chiefly through publications, diagrams, citations and implementations. My DDR archival history and his operational archaeology therefore overlap in method but are not interchangeable.

# The author's main move

**The chapter's proposition:** Machine learning's altered programmability becomes intelligible through movements between kinds of diagrams—tables, formal equations, coding procedures, learned parameters, pedagogical inscriptions, scientific publications and executable infrastructures. A diagram is here an *operational arrangement of relations*, not merely a graphic explaining a finished system (especially pp. 22, 41–43, 49–50). Attending to these movements makes possible an immanent, materially specific critique rather than attributing agency to a generic 'algorithm'.

## Claim 1 — Programmes do not simply grow themselves; machine learning is distributed work

**Author claim:** Mackenzie questions the analogy, borrowed from Pedro Domingos, that learning resembles farming more than constructing a program, because 'grown' learners depend on extensive documentary, technical and institutional arrangements. **Evidence-supported claim:** The opening inventory includes code, publications, software tools, data-centre architectures, visual media and discussion, and the chapter proposes following this distributed formation through Python, R and libraries (pp. 21–22). ## Claim 2 — Code makes operations inspectable but does not contain the whole phenomenon

**Author claim:** Code both reveals and obscures the operational formation: it can be read and experimentally modified, but no code listing is sufficient to diagram all the ways learners 'make' programs. **Evidence-supported claim:** Mackenzie locates programming within mathematical formalisation, scientific knowledge, infrastructure and economics (p. 22), and observes that Python and R acquired a shared repertoire of routines for processing data and fitting models (p. 23). **Warrant:** A repository can disclose implementation logic without, on its own, showing why a dataset was selected, which practices trained a user, which dependency created a representation or which disciplinary expectations shaped a result. **My inference:** The DDR GitHub code and model documentation should be read together with archival decisions, research notes and the finished interface; none substitutes for the other. **Boundary:** This is an argument for *additional sites of inspection*, not grounds for dismissing code review, tests or reproducibility. **Consequence:** Design the methods account as a traceable chain among source, metadata, transform, model and inquiry rather than a code inventory. **Practice cross-check:** Compare a DDR retrieval path across repository implementation, evidence-card UI and source documents; **TODO (specific commit and record IDs)**. ## Claim 3 — Learning re-expresses symbolic propositions as adjusted numerical parameters

**Author claim:** The shift from conventional programming to machine learning can be glimpsed when a logical problem expressed as a Boolean truth table is reconstituted as numerical training examples and learned through weight adjustment. **Evidence-supported claim:** **Table 2.1** gives the NAND truth table (p. 24); **Listing 2.2** supplies Python perceptron code (p. 25); **Table 2.2** presents successive weight values (p. 26); and the text explains that iterations adjust weights against target outputs until the stopping condition is met (pp. 26–27). **Warrant:** The learned numerical parameters need not reproduce the symbolic rule in a directly readable form; 'learning' depends on the conversion of a proposition to training data and a procedure for measuring error. **My inference:** The textual concepts in the DDR record likewise do not persist unchanged when projected into vectors: the model output is a numerical representation made usable for a specified operation, not the source's own historical assertion. **Boundary:** A simple perceptron trained on a Boolean exercise is a deliberately elementary illustration; it does not explain a present-day text-embedding architecture. **Consequence:** I should explain how an archival statement is transformed before similarity search and where semantic equivalence can legitimately be claimed. **Practice cross-check:** Inspect a single PID-linked passage, its chunk and its nearest-neighbour retrieval, recording how textual wording maps to the computational task; **TODO (source and query IDs)**. ## Claim 4 — Learning the field is itself an object of research, not neutral preparation

**Author claim:** What counts as machine-learning competence takes shape through repeated engagement with books, online courses, code libraries, exercises and research publications. **Evidence-supported claim:** Mackenzie recounts attending courses, taking part in online learning and competitions, copying mathematical statements and using multiple programming environments (pp. 27–29). **Figure 2.1** on p. 28 depicts his accumulated knowledge as a hand-drawn 'network-cloud' rather than a tidy progression. He then observes that course and textbook curricula have become increasingly standardised around regression, neural networks, decision trees, support vector machines and model-selection questions (pp. 29–30). **Warrant:** Pedagogy and common examples select which operations seem elementary, authoritative and repeatable; those selections shape practitioners before any model is deployed. **My inference:** The researcher's route into embedding models, vector databases and evaluation frameworks is part of the situated practice history of DDR's instrument. **Boundary:** A personal account of learning does not establish that all practitioners share the same educational route; Mackenzie also recognises variations in textbook emphases (p. 31). **Consequence:** Research reflection should record why methods were learned, chosen, revised or rejected, not merely their final technical specifications. **Practice cross-check:** Examine the practice journal's model-selection rationale and retrospective learning notes; **TODO (add dated entries)**. ## Claim 6 — Software dependencies are material, epistemic and collective relations

## Claim 9 — Diagrammatic transformations migrate between explanatory regimes and working systems

**Author claim:** The continuing development of machine learning can be followed in the migration and substitution of representational forms; diagrams become implemented machines and functioning machines make further diagrams. **Evidence-supported claim:** **Figure 2.6** compares Rosenblatt's 1958 perceptron diagram with a later neural-network diagram: the former retains neuro-anatomical labels while the latter uses formalised mathematical variables (p. 47). # Definitions / operational vocabulary

- **Diagram (as Mackenzie develops it):** An arrangement of relations capable of operating across mathematical, graphical, textual and software forms (pp. 41–43, 49). **My working use:** Any inspectable representation of the DDR instrument that identifies actual operations and their relations, not simply any decorative illustration.
- **Statistical algorithmic diagram:** The learned-parameter approach to a problem where an explicitly symbolic rule may have been programmed directly; developed through the perceptron exercise (pp. 23–27). **My use:** A reminder that the representation produced from archival text belongs to a modelling task and cannot be conflated with the source statement.
- **Operational formation:** Relations among scientific publications, pedagogical routines, code, mathematical forms, datasets, tools and infrastructures (pp. 22–23, 49–50). **My use:** The wider material and intellectual context within which the DDR evidence apparatus works.
- **Diagrammatic movement/substitution:** Translation and modification among code, graphical forms and mathematical statements in the design or execution of models (pp. 42–43, 48–49). **My use:** A way to document changes in the form and permissible interpretation of DDR traces along the computational pipeline.
- **Dependency:** In Mackenzie's R example, software packages and configured resources required or suggested for operational execution (pp. 37–40). **My use:** Versioned technical constituents whose behaviour may affect outputs. **Boundary:** Repository dependency lists alone cannot attest historical provenance or interpretative accuracy.
- **Learned weights / parameters:** Numerical values adjusted through the perceptron's iterative fitting of training cases (pp. 25–27). **My use:** A useful conceptual distinction between fitted model representation and the human-readable source from which learning data may originate.

# My response and critical assessment

This chapter is especially useful to a designer because Mackenzie gives the term **diagram** more responsibility than communication or explanation: his diagrams join representational form to operations that can be taught, copied, manipulated, instantiated and transformed. The source's strongest move is its specificity. The Boolean example, annotated regression equation, R dependency chain and changing perceptron drawings are materially different evidence, which keeps a broad theoretical claim from becoming free-floating metaphor (pp. 23–27, 37–43, 46–49). **Figure 2.1** (p. 28) and **Figure 2.5** (p. 45) are especially pertinent to practice-led research: they show learning and drawing as situated activities within the author's method, not merely illustrations appended after the argument.

A reservation follows from that same strength. The argument sometimes moves from accessible *examples of diagrammatic transformation* to a wide account of the 'operational formation' without empirically tracing every institutional or economic relation it invokes. The chapter is strongest as a **research procedure**—follow operations through their different material inscriptions—rather than as a claim that a diagram can itself settle questions of power, agency or historical influence. It is particularly significant that Mackenzie explicitly limits his own archive-based historical reconstruction (pp. 47–48, note 9). For DDR, I therefore need both the operational tracing he models and the primary archival criticism he does not undertake here.

**Reusable thesis sentence:** *I treat the DDR research instrument as a diagrammatic and operational assemblage: its texts, models, mathematical representations, code and interfaces are successive but non-equivalent mediations whose design must be examined alongside the historical evidence they make available.*

# Boundary + risk

**Boundary:** Mackenzie's cases concern pre-2017 statistical learning, a perceptron, R libraries, scientific citation circulation and mathematical pedagogy. This chapter contains no tests of contemporary semantic embeddings, UMAP projections, retrieval-augmented inference or LLM-based historical synthesis.

**Risk of misuse:** To say that my framework is 'diagrammatic' because it contains arrows would trivialise Mackenzie's claim. The value arises only when an arrow stands for a demonstrable representational or operational change whose consequences I can examine.

# Cross-source / cross-lens synthesis

Chapter 1 argued that machine learning should be investigated as a heterogeneous practice of knowledge production rather than described by abstract technological agency. Chapter 2 gives that programme workable material sites: a truth table turned into fitted parameters, an authoritative textbook transformed into an uneven citation network, a mathematical expression reread as a diagram, a one-line installation command unfolded into distributed dependencies, and a historical drawing restated as a different formal arrangement (pp. 23–27, 30–40, 41–43, 46–50). Together these chapters strengthen the **critical computational approaches** lens by making *how* representations come into being a matter of empirical examination. They also complicate my practice-led position: building a system is insufficient without evidence that the making disclosed something about its interpretative limits. The new working proposition is that I can mobilise DDR traces responsibly by designing computational pathways that make their transformations visible and reversible to source inspection. That proposition still requires **documented DDR cases**, and the implications for archival description, contested design history and situated authorship must be tested within their own evidence traditions.
